# 適合アプリ作成ガイド

対象読者:
- LabWebSystem に新しい Web アプリを登録したい開発者

文書ステータス:
- current

最終更新日:
- 2026-06-07

## 1. 目的
このガイドは、LabWebSystem の routing / domain / appdata 運用にそのまま載せられる GitHub リポジトリを、安全に作るための説明書です。

## 2. 最初に理解すること
LabWebSystem に登録するアプリは、単に Docker Compose が起動すればよいわけではありません。次の前提に合わせる必要があります。

1. ブラウザは `https://<hostname>` へアクセスする
2. reverse proxy が `hostname -> web service` の経路を張る
3. フロントエンドは same-origin の `/api/*` を使って API へ到達する
4. `web` と `api` は compose の内部ネットワークでつながる
5. 永続データは `APPDATA_ROOT` を通じて `LAB_CORE_APPDATA_ROOT` 配下へ出す

構成の全体像は `docs/readmes/LabWebSystem適合アプリ構成図.md` を参照してください。

## 3. 推奨リポジトリ構成
```text
my-app/
├── docker-compose.yml
├── docker-compose.dev.yml
├── labcore.app.yaml
├── labcore/
│   ├── profiles/
│   │   ├── dev-sim.yaml
│   │   ├── dev-real-device.yaml
│   │   └── prod.yaml
│   ├── seeds/
│   └── SDK使い方.md
├── package.json
├── README.md
└── src/...
```

`labcore init` を使うと、この構成のひな形と `labcore:lint` などの scripts をまとめて生成できます。

## 4. Compose の基本ルール
### 4.1 `docker-compose.yml` は配備用
- reverse proxy 配下で使う前提なので、公開対象サービスには `ports:` ではなく `expose:` を使う
- manifest の `exposure.service` と `exposure.port` に一致する `web` サービスを置く
- `prod` profile では原則としてこの compose だけを使う

例:
```yaml
services:
  web:
    build:
      context: .
      dockerfile: Dockerfile
    restart: unless-stopped
    environment:
      PORT: "4173"
    expose:
      - "4173"
```

### 4.2 `docker-compose.dev.yml` は localhost 用
- 単体確認のための `ports:` はここへ分離する
- `dev-sim` / `dev-real-device` profile からだけ読み込む

例:
```yaml
services:
  web:
    ports:
      - "${LOCAL_WEB_PORT:-5180}:4173"
```

## 5. フロントエンドと API の接続
### 5.1 same-origin を既定にする
- ブラウザから見える `localhost` は利用者端末です
- `http://localhost:8787` 固定は、配備後に高確率で破綻します
- 既定値は `VITE_API_BASE_URL=/` にして、アプリ内部では空文字として扱う構成を推奨します

### 5.2 proxy は `web -> api` で張る
- Vite などの開発サーバーでは `web` コンテナから `api` コンテナへの proxy を張る
- 例: `VITE_PROXY_TARGET=http://api:8787`

## 6. 永続データの扱い
LabWebSystem では `LAB_CORE_APPS_ROOT` と `LAB_CORE_APPDATA_ROOT` を分けて管理します。  
そのため、LabWebSystem 配備向けサンプルでは Docker named volume より `APPDATA_ROOT` bind mount を推奨します。

例:
```yaml
services:
  db:
    volumes:
      - ${APPDATA_ROOT:-../../appdata/my-app}:/var/lib/postgresql/data
```

localhost 開発では profile から `APPDATA_ROOT=./.appdata/my-app` を上書きすると扱いやすくなります。

## 7. `hostname` と root domain
- `labcore.app.yaml` の `exposure.hostname` は登録される最終値です
- localhost 開発の既定値には `*.lab.localhost` を使って構いません
- 本番配備前には `app.<LAB_CORE_ROOT_DOMAIN>` へ更新する運用を標準にしてください

例:
- localhost 開発: `homepage.lab.localhost`
- 研究室配備: `homepage.fukaya-sus.lab`
- 独自ドメイン配備: `homepage.example.com`

## 8. profile の推奨ルール
### 8.1 `dev-sim`
- `docker-compose.yml`
- `docker-compose.dev.yml`
- `LABCORE_DEVICE_MODE=mock`
- `APPDATA_ROOT=./.appdata/<app-name>`

### 8.2 `dev-real-device`
- `docker-compose.yml`
- `docker-compose.dev.yml`
- `LABCORE_DEVICE_MODE=real`
- 必要ならデバイスパスを明示

### 8.3 `prod`
- `docker-compose.yml` のみ
- `LABCORE_DEVICE_MODE=real`
- `docker-compose.dev.yml` を混ぜない

## 9. やってはいけない例
- フロントエンドで `http://localhost:<port>` を固定する
- 配備用 `docker-compose.yml` に `ports:` を残す
- `prod` profile に `docker-compose.dev.yml` を混ぜる
- 永続データをコンテナ内だけに閉じる
- `hostname` を `*.lab.localhost` のまま本番登録する

## 10. SDK を使った確認手順
```bash
yarn add -D @lab-core/sdk-cli@https://github.com/LabWebSystem/LabWebSystem-Core.git#workspace=@lab-core/sdk-cli&head=main
yarn labcore:lint
yarn labcore:preflight
yarn labcore:guard
yarn labcore:export
```

`labcore init` で生成される `package.json` には上記 scripts が入ります。  
`lint` / `doctor` では、次のような運用上の危険も警告されます。

- 配備用 compose に `ports:` がある
- runtime 設定に `localhost` が混ざっている
- `APPDATA_ROOT` が使われていない
- `prod` profile に `LABCORE_DEVICE_MODE` がない
- `hostname` が `*.lab.localhost` のままになっている
