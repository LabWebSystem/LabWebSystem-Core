# ダッシュボード機能要素整理

## 目的

この文書は、現行ダッシュボードが持つ機能を、画面構成や文言配置から切り離して抽象化したうえで、各 UI が必要とするバックエンド API 連携を詳細化したものである。  
UI を再構成する際に必要となる「何を入力し」「どの API に送信し」「どの型で受け取り」「画面内部でどう状態遷移するか」を整理する。

## API 連携の共通仕様

### ベース URL

- フロントエンドは `VITE_API_BASE_URL` を基準 URL とし、各 API パスを連結して通信する。
- 実際の呼び出し形式は `fetch(${VITE_API_BASE_URL}${path})` である。

### 共通ヘッダー

- 全 API 呼び出しで `Content-Type: application/json` を付与する。

### エラー処理

- HTTP ステータスが `2xx` 以外の場合、レスポンス JSON の `message` を優先してエラーメッセージとして扱う。
- `message` が無い場合は `HTTP <status>` の文字列を利用する。
- 各 UI はこのエラー文字列を受け取り、失敗通知や送信抑止に利用する必要がある。

### 共通の UI データフロー

- API 実行前に、UI 側は処理中フラグを立てる。
- API 実行後、成功時は一覧系データや詳細データを再取得する。
- 失敗時は入力値を保持したまま、失敗通知とエラー表示のみを更新する。
- 一部機能はバックエンドでジョブを生成して非同期実行されるため、即時の完了結果ではなく「処理開始結果」を受け取る前提で設計する必要がある。

## 共通して必要な基盤 UI

### 1. システム状態表示 UI

#### API

- `GET /api/system/status`
- フロントエンド関数: `fetchSystemStatus()`
- レスポンス型: `SystemStatus`

#### データフロー

- UI 初期化時に API を呼ぶ。
- 一定時間ごと、および画面再フォーカス時に再取得する。
- 取得結果は実行モード、ルートドメイン、集計表示、DNS 関連表示の元データになる。

#### UI 上で必要なこと

- ローディング状態の保持
- 最終取得結果の保持
- 再取得失敗時のエラー表示

### 2. アプリ集合表示 UI

#### API

- `GET /api/applications`
- フロントエンド関数: `fetchApplications()`
- 生レスポンス型: `{ applications: ApplicationListItem[] }`
- UI 利用時の実効型: `ApplicationListItem[]`

#### データフロー

- 全体再取得時に API を呼ぶ。
- レスポンスの `applications` を UI 表示用状態へ格納する。
- ここで得た `application_id` が詳細取得、ログ取得、各操作 API の入力元になる。

#### UI 上で必要なこと

- 一覧表示
- 選択対象の識別子保持
- 既存データからの状態別抽出、ソート、強調表示

### 3. イベント履歴表示 UI

#### API

- `GET /api/events?limit=<number>`
- フロントエンド関数: `fetchEvents(limit?: number)`
- 生レスポンス型: `{ events: SystemEvent[] }`
- UI 利用時の実効型: `SystemEvent[]`

#### データフロー

- 全体再取得時に上限件数を付けて取得する。
- レスポンスの `events` を時系列表示用状態へ格納する。
- 関連アプリ識別子や重要度は、導線や強調色の条件に利用する。

#### UI 上で必要なこと

- 上限件数を保持する仕組み
- レベルごとの区別表示
- 関連対象への移動導線

### 4. ジョブキュー表示 UI

#### API

- `GET /api/jobs?limit=<number>`
- フロントエンド関数: `fetchJobs(limit?: number)`
- 生レスポンス型: `{ jobs: ApplicationJob[] }`
- UI 利用時の実効型: `ApplicationJob[]`

#### データフロー

- 全体再取得時にジョブ一覧を取得する。
- レスポンスの `jobs` をキュー表示用状態へ格納する。
- `status`、`retryable`、`cancellable`、`dismissible` に応じて UI で可能操作を切り替える。

#### UI 上で必要なこと

- 状態別件数集計
- 経過時間表示
- 関連アプリ導線
- 再実行、取消、削除の操作導線

### 5. 明示的な再取得 UI

#### API

- 個別の専用 API は無い
- 実際には以下を並列実行する
  - `GET /api/system/status`
  - `GET /api/applications`
  - `GET /api/events?limit=<number>`
  - `GET /api/jobs?limit=<number>`

#### データフロー

- 利用者が再取得操作を行う。
- UI 側で処理中状態を立てる。
- 4 系統の API を並列実行し、成功後に全状態を置き換える。
- 失敗時はエラーメッセージのみ更新する。

### 7. 最近追加アプリ抽出 UI

#### API

- 新規 API は不要
- 入力元は `ApplicationListItem[]`

#### データフロー

- 一覧取得後のローカル状態から `created_at` で並べ替える。

### 8. 失敗ジョブ抽出 UI

#### API

- 新規 API は不要

## アプリ登録のための UI

### 9. 登録元解析 UI

#### API

- `POST /api/applications/import/resolve`
- フロントエンド関数: `resolveImportSource(sourceUrl: string)`
- リクエストボディ型:
  - `{ sourceUrl: string }`
- レスポンス型:
  - `ImportResolveResponse`

#### バックエンドで期待される処理

- URL 正規化
- ブランチ解決
- リポジトリ内ファイル探索
- `labcore.app.yaml` の検出と解析
- compose 候補の推定

#### データフロー

- 利用者がリポジトリ URL を入力する。
- UI は URL 文字列を API に送る。
- 成功時、`ImportResolveResponse` をローカル状態へ保存する。
- 同時に `manifest` 由来の初期値で以下を埋める。
  - 名前
  - 説明
  - ブランチ
  - compose パス
  - 公開サービス
  - 公開ポート
  - ホスト名
  - 実行モード
  - データ保持設定
  - デバイス要件
  - 環境変数上書き初期値
- `recommendedComposePath` があれば、続けて構成ファイル解析 UI の API を自動実行する。

#### 補足制約

- レスポンスには `manifest` が必須であり、不正形式時はフロントエンド側でエラー化している。

### 10. 構成ファイル解析 UI

#### API

- `POST /api/applications/import/compose-inspect`
- フロントエンド関数: `inspectComposeFile(repositoryUrl: string, branch: string, composePath: string)`
- リクエストボディ型:
  - `{ repositoryUrl: string; branch: string; composePath: string }`
- レスポンス型:
  - `ImportComposeInspectResponse`

#### バックエンドで期待される処理

- 対象 compose の取得
- YAML 解析
- サービス候補抽出
- ポート推定
- 環境変数要件抽出
- デバイス要件抽出

#### データフロー

- UI は登録元解析結果または利用者指定の compose パスを持つ。
- API 実行後、`ImportComposeInspectResponse` を構成解析状態として保持する。
- `services` を公開候補一覧の表示に使う。
- `environmentRequirements` を環境変数入力欄の自動生成に使う。
- `detectedDeviceRequirements` をデバイス要件初期値へ補完する。
- UI は `likelyPublic` と `detectedPublicPort` を使って推奨サービスを自動選択する。

#### 補足制約

- `parseError` がある場合、登録送信前に利用者へ明示する必要がある。
- `rawYaml` と `parsedYaml` は詳細確認 UI のために保持する必要がある。

### 11. 登録内容編集 UI

#### API

- 直接 API は呼ばない
- 送信先は新規登録実行 UI の API

#### 内部で保持すべき入力型

- `name: string`
- `description: string`
- `repositoryUrl: string`
- `defaultBranch: string`
- `composePath: string`
- `publicServiceName: string`
- `publicPort: string` または送信直前に `number`
- `hostname: string`
- `mode: "standard" | "headless"`
- `keepVolumesOnRebuild: boolean`
- `deviceRequirementsRaw: string`
- `environmentOverrides: Record<string, string>`

#### データフロー

- 解析結果から初期値を受け取る。
- 利用者編集をローカル状態として保持する。
- 送信直前に以下の正規化を行う。
  - 文字列 trim
  - `publicPort` の数値化
  - `deviceRequirementsRaw` のカンマ区切り配列化
  - 空の環境変数上書きの除外

### 12. 新規登録実行 UI

#### API

- `POST /api/applications`
- フロントエンド関数: `createApplication(payload: CreateApplicationPayload)`
- リクエストボディ型:
  - `CreateApplicationPayload`
- レスポンス型:
  - `CreateApplicationResponse`

#### バックエンドで期待される処理

- 入力検証
- アプリ定義保存
- デプロイ準備
- ルート設定生成
- ジョブ生成

#### データフロー

- UI は編集済み入力値から `CreateApplicationPayload` を組み立てる。
- 送信前検証:
  - リポジトリ URL 必須
  - 登録元解析完了必須
  - compose 解析完了必須
  - composePath 存在必須
- 成功時:
  - 入力状態を初期化
  - 一覧系データを再取得
  - `CreateApplicationResponse.applicationId` を選択対象候補に使う
- 失敗時:
  - 入力保持
  - エラー表示

## アプリ運用のための UI

### 13. 個別アプリ詳細取得 UI

#### API

- `GET /api/applications/:applicationId`
- フロントエンド関数: `fetchApplicationDetail(applicationId: string)`
- パスパラメータ:
  - `applicationId: string`
- レスポンス型:
  - `ApplicationDetail`

#### データフロー

- 一覧から選択された `application_id` を入力にする。
- 成功時:
  - `ApplicationDetail` を詳細状態として保持する
  - `deployment` からデプロイ編集用の初期値を構築する
  - `composeInspection` から構成解析状態を構築する
- この API は定期再取得の対象でもある。

#### 補足制約

- 編集中のデプロイ設定がある場合、再取得しても入力を上書きしない制御が必要である。

### 14. アプリ停止 UI

#### API

- `POST /api/applications/:applicationId/stop`
- フロントエンド関数: `stopApplication(applicationId: string)`
- リクエスト型:
  - ボディなし
- レスポンス型:

#### データフロー

- UI は対象アプリ識別子を送る。
- 成功時:
  - 成功通知を表示
  - 一覧と詳細を再取得

- 成功後:
  - 削除ジョブ開始通知
  - 詳細状態の破棄
  - 一覧へ戻る
  - 一覧とジョブを再取得

## デプロイ設定編集のための UI

### 22. 現在設定読込 UI

#### API

- 専用 API は無い
- 実際には `GET /api/applications/:applicationId` の `ApplicationDetail.deployment` を利用する

#### データフロー

- 詳細取得成功時に `ApplicationDetail.deployment` を `UpdateDeploymentPayload` 相当の編集状態へ写像する。
- 同時に `ApplicationDetail.composeInspection` を既存解析結果として読み込む。

### 23. 既存アプリ向け構成ファイル再解析 UI

#### API

- `POST /api/applications/:applicationId/deployment/inspect`
- フロントエンド関数: `inspectApplicationDeploymentCompose(applicationId: string, composePath: string)`
- リクエストボディ型:
  - `{ composePath: string }`
- レスポンス型:
  - `ApplicationComposeInspection`

#### データフロー

- UI はアプリ識別子と compose パスを送る。
- 成功時:
  - `services` を候補一覧へ反映
  - `environmentRequirements` を編集入力へ反映
  - 推奨サービスを使って `publicServiceName` と `publicPort` を補正
  - `selectedComposePath` を現在選択値へ反映

#### 補足制約

- 失敗時は既存編集内容を保持しつつ、解析状態のみエラーにする。

### 24. デプロイ設定編集 UI

#### API

- 直接 API は呼ばない
- 送信先はデプロイ設定保存 UI の API

#### 内部で保持すべき入力型

- `composePath: string`
- `publicServiceName: string`
- `publicPort: string` または送信直前に `number`
- `hostname: string`
- `keepVolumesOnRebuild: boolean`
- `envOverrides: Record<string, string>`

#### データフロー

- 詳細取得または構成ファイル再解析から初期値を受け取る。
- 利用者編集をローカル状態として保持する。
- 別の compose を選んだ際は再解析 API を実行し、候補と入力値を同期する。

### 25. デプロイ設定保存 UI

#### API

- `PATCH /api/applications/:applicationId/deployment`
- フロントエンド関数: `updateApplicationDeployment(applicationId: string, payload: UpdateDeploymentPayload)`
- リクエストボディ型:
  - `UpdateDeploymentPayload`
- レスポンス型:
  - フロントエンドは本文を利用していない

#### 送信前検証

- `parseError` が存在しないこと
- `publicServiceName` が空でないこと
- 候補が存在する場合は候補内に含まれること
- `hostname` が空でないこと
- `publicPort` が `1..65535` の整数であること

#### データフロー

- UI は編集状態を `UpdateDeploymentPayload` へ正規化する。
- 成功後:
  - 成功通知
  - 一覧再取得
  - 詳細再取得
  - 未保存変更フラグ解除

## ログ確認のための UI

### 26. ログ対象サービス取得 UI

#### API

- `GET /api/logs/:applicationId/services`
- フロントエンド関数: `fetchApplicationLogServices(applicationId: string)`
- レスポンス型:
  - 生レスポンス `{ services: string[] }`
  - UI 利用時の実効型 `string[]`

#### データフロー

- ログ UI を開く際に対象アプリ識別子で取得する。
- `services` を選択候補として保持する。
- 既定サービスは、一覧上の公開サービス名を優先し、無ければ先頭要素を使う。

### 27. ログ取得 UI

#### API

- `GET /api/logs/:applicationId?service=<string>&tail=<number>`
- フロントエンド関数:
  - `fetchApplicationLogs(applicationId: string, options?: { service?: string; tail?: number })`
- クエリパラメータ:
  - `service?: string`
  - `tail?: number`
- レスポンス型:
  - `ApplicationLogsResponse`

#### データフロー

- ログ UI 初期化時:
  - まずサービス一覧取得
  - 次に既定サービスと既定行数でログ取得
- 自動更新時:
  - 現在の `selectedService` と `tail` をそのまま再送
- 成功時:
  - `lines` をログ本文表示へ反映
  - `fetchedAt` を取得時刻表示へ反映

#### UI 上で必要な状態

- `opened: boolean`
- `services: string[]`
- `selectedService: string`
- `tail: number`
- `lines: string[]`
- `lastFetchedAt: string`
- `loading: boolean`
- `autoScroll: boolean`
